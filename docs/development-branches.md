# 分支与发布工作流

## 推荐结构

星笺采用小团队的短分支工作流：

- `main` 只保留可发布或已发布状态，发布用 tag 标记，例如 `v0.2.4`。
- 每个功能或修复使用一个短期 `codex/<topic>` 分支；一个分支只解决一个主题。
- 完成后先做定向检查，再合并回 `main`；合并后删除远端和本地短分支。
- 只有发布准备确实需要多人并行稳定时才建立 `release/<version>`，发布结束立即关闭。
- 线上紧急修复从最新 tag 或 `main` 建立 `hotfix/<topic>`，验证后合并回 `main` 并补发新 tag。
- 不长期维护一个与 `main` 平行的 `develop` 分支，也不把验收记录、临时实验和多个功能堆进同一个功能分支。

## 合并后核对

- 核对每个 PR 的服务器状态与 main 提交历史，不能把创建 PR 当作已合并。
- 比对开始时的文件快照与最终 main，避免拆分遗漏。原工作区如有同期修改，另存并核对；本轮已合入的旧差异保留为本地 stash 后再同步 main。
- 原生平台结果只覆盖 CI 实际执行的构建、权限、CLI、字体与安装场景；Markdown 原生 PNG 导出、聊天软件多图粘贴和最终拖放收件仍有独立验收边界。

## 历史分支判断

历史功能使用过 squash 合并，旧分支的原提交未必成为 main 的祖先。`git branch --no-merged main` 不能单独证明功能没有合并；应结合 PR 合并状态、合并提交和实际文件内容判断。历史分支数量本身也不能证明项目不成熟。清理前核对分支有无合并后的新增工作及其他工作区占用，不能只按祖先关系批量删除。
