# 数据结构升级与跨版本兼容

软件版本、SQLite 结构版本、历史 JSON 版本和统计协议是独立编号。新结构不能只修改版本常量；必须保留仍受支持的旧库入口、转换规则与数据保护。

## 完整恢复点与实际迁移

结构升级前，`Store::open_with_recovery` 先以只读连接检查旧库，再通过 SQLite `VACUUM INTO` 保存全库一致快照：所有表、索引及已提交数据（含图片、偏好、本地活动计数），并包含已提交的 WAL 数据。恢复点目录另复制已下载字体、旧纸张缓存、受管渲染器与相关选择设置，不递归复制已有恢复点。它不只是备份将要修改的表，也不是直接复制正在变化的数据库文件。

随后在原数据库的事务里补齐缺失列、表和索引、转换必要的数据。需要移除旧表级唯一约束时会重建相关表；旧单图 BLOB 表不因新增图集表而整体复制到另一个工作数据库。全部完成并校验后才提交目标 `user_version`；任一步失败回滚，升级前恢复点保留。已有历史保留设置仍按原有启动规则执行，恢复点在该清理之前创建。

软件安装前的 `before-update` 与结构迁移前的 `before-migration` 是独立保护点，可能各有一份完整副本。跨版本直升的数据迁移入口只在整个迁移开始前保存一份，不为内部每条 SQL 再复制整库；成功后重开当前结构不重复建立迁移快照。2026-11-04 用户明确要求升级成功后去掉旧版本数据。新版正常打开并通过当前库校验后，旧应用版本或旧结构的自动副本即按 [清理策略](recovery-retention.md) 删除；迁移失败时恢复点保留，手动备份由用户管理。

## 逐级与跳级

当前开发结构为 5，生产迁移采用累计补齐流程：根据旧库实际形状应用仍缺少的转换，因此可从支持的旧结构直接进入 5，用户无需逐个安装中间软件版本。

| 输入结构 | 当前处理 |
| --- | --- |
| 0（原始旧库）/ 1 / 2 | 补齐列、图片 / 隐私 / 文件明细与身份空间、富文本 / 统计 / 搜索及图集支持，事务到 5 |
| 已识别旧分支 3 | 先严格校验六表、列、约束、索引、外键与文件明细，再进入统一结构；保留已知文件类型与顺序 |
| 4 | 保留旧记录、身份与资源，新增图集存储及严格图片去重索引，到 5 |
| 5 | 校验当前结构，沿既有启动维护路径打开；不重复迁移 |
| 未识别的 3 / 高于当前支持范围 | 拒绝写入，不伪装成空库或自动降级 |

用户 2026-11-03 明确要求同时考虑逐版本升级和跳过部分版本升级。后续每次结构变更须保留仍受支持的旧入口，验证「上一结构 → 新结构」「各支持旧结构 → 新结构」与连续升级后所得数据形状，并检查失败回滚、重复启动、完整快照。不能假设用户安装过所有中间版本，也不能把分支曾占用的结构号视为自动兼容。

## 验证边界

`store/migration_tests.rs` 从原始结构开始，使用冻结 DDL 构造逐级演进的旧结构夹具；独立验证 0 / 1 / 2 / 已识别 3 / 4 直升当前结构，以及旧分支 3 → 统一 4 夹具 → 5。覆盖记录 ID / 时间 / 计数、图片原字节、文件类型与顺序、同路径文本独立身份、隐私 / 手动标签、分组、偏好、富文本、已有活动计数、全表快照及资源副本、重开幂等。

这些是原创存储夹具回归，不表示本轮执行了每个历史安装包。历史真实安装升级证据与本轮检查分别见 [验证记录](verification.md)。未使用真实剪贴内容或正式数据库进行迁移测试。
